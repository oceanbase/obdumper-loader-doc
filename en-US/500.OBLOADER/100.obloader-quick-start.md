# Getting started

This topic shows you how to use the derivative tool.

## Step 1: Download the software

<main id="notice" type='explain'>
   <h4>Note</h4>
   <p>Derivative Tool V4.2.1 and later versions no longer differentiate between the enterprise edition and the community edition. Users can download the software package from the community download center.</p>
</main>

[Download](https://en.oceanbase.com/softwarecenter?_gl=1*nejld*_ga*NDQ5MTc4NTEuMTY3NTIzOTgyOA..*_ga_T35KTM57DZ*MTY4Mzg1ODgwNC44MC4xLjE2ODM4NTg4NTYuOC4wLjA.) the latest version of the Derivative Tool software package and decompress it:

```shell
unzip ob-loader-dumper-4.3.x-RELEASE.zip
cd ob-loader-dumper-4.3.x-RELEASE
```

## Step 2: Configure the runtime environment

<main id="notice" type='notice'>
   <h4>Notice</h4>
   <p>Java 8+ must be installed in the local environment and the <code>JAVA_HOME</code> environment variable must be configured. We recommend that you install JDK 1.8.0_3xx or later. For more information, see <a href="../400.deployment-guide/100.environmental-preparation.md">Prepare the environment</a>. </p>
</main>

A small JVM memory size may affect the performance of import and export operations and even the stability of the import and export features. You can specify the JVM memory size by using the `--mem` parameter. For example, `--mem 4G`.

## Step 3: Prepare the data

When you use the OBLOADER import feature, you can use an existing data file or generate a data file by using the TPC-H tool. The content of the imported file must conform to the specifications. For more information about how to identify the data format in the file, see [Have you prepared your data?](https://open.oceanbase.com/blog/1100272).

## Step 4: Create a database

1. Use the OCP console or the OBD command-line tool to create an OceanBase cluster.

2. Create a test database.

3. Create a test table and insert data into it. (This step is optional.)

## Step 5: View the configuration file

The configuration file of the data migration tool includes the connection configuration file (`session.config.json`) and the log file (`log4j2.xml`).

### Connection configuration file

The connection configuration file (`{ob-loader-dumper}/conf/session.config.json`) is used to configure the database connection parameters. When connecting to the database, the data migration tool constructs a JDBC URL using the JDBC parameters in the connection configuration file and executes the initialization SQL statements in the new connection. You can modify the JDBC parameters and initialization SQL statements in the connection configuration file. The default values of the connection configuration apply to most scenarios. However, in some special cases, you may need to manually modify these parameters to adapt to different OBServer versions and ETL scenarios. For more information about the connection configuration, see [Connection configuration](../800.obloaderobdumper-session-variables.md).

### Log configuration file

The log configuration file (`{ob-loader-dumper}/conf/log4j2.xml`) is used to view the log output path and log format, and to adjust the log level when [troubleshooting](../900.obloaderobdumper-self-help-guide.md). For more information about how to customize the log file name of an export job, see [How to customize the log file name of an export job](600.obloader-faq.md).

## Step 6: Import data

```shell
./obloader -h 'IP address' -P'port' -u'username'@'tenant name'#'cluster name' -p'password' -D'database name' --table 'table name' --csv -f 'file path' --sys-password 'sys tenant password' --external
```

<main id="notice" type='explain'>
   <h4>Note</h4>
   <p>This example only imports data without schema. For more information, see <a href="200.obloader-command-line-options.md">OBLOADER command-line options</a>. </p>
</main>

The following table describes the database information used in the example:

|              **Database information**              |   **Example value**    |
|-------------------------------------|--------------|
| Cluster name                                 | cluster_a    |
| OceanBase Database Proxy (ODP) host address | xx.x.x.x     |
| OceanBase Database Proxy (ODP) port number  | 2883         |
| Tenant name of the cluster                              | mysql        |
| Username of the root/proxyro user in the sys tenant |\*\*u\*\*\*|
| Password of the root/proxyro user in the sys tenant          | \*\*\*\*\*\* |
| Username of the user in the business tenant (with read and write permissions)                  | test         |
| Password of the user in the business tenant                          | \*\*\*\*\*\* |
| Schema name                           | USERA        |

**Scenario**: Import all supported database object definitions from the `/output` directory into the USERA schema (for OceanBase Database versions earlier than V4.0.0, provide the password of the sys tenant).

**Sample statement**:


### Import POS data files

**Scenario**: Import all supported POS data files from the `/output` directory into the USERA schema (for OceanBase Database versions earlier than V4.0.0, provide the password of the sys tenant). When importing, specify the path where the control file is located. POS data files (with the default .dat extension) are organized by fixed-length byte offsets. During import, use the control file to define the fixed length for each field. These files can be opened directly using a text editor.

**Sample statement**:

```shell
$./obloader -h xx.x.x.x -P 2883 -u test@mysql#cluster_a -p ****** --sys-user **u*** --sys-password ****** 
-D USERA --table '*' -f /output --pos --ctl-path /output
```

  <main id="notice" type='explain'>
    <h4>Note</h4>
    <p>The table names defined in the database must match the case of the corresponding control file names. Otherwise, OBLOADER cannot recognize the control files. For more information about the control file definition rules, see <a href="300.obloader-data-processing/200.obloader-preprocessing-functions.md">Preprocessing functions</a>.</p>
  </main>

### Import CUT data files

**Scenario**: Import all supported CUT data files from the `/output` directory into the USERA schema (for OceanBase Database versions earlier than V4.0.0, provide the password of the sys tenant). CUT data files (with the .dat extension) are data files separated by single characters or strings. These files can be opened directly using a text editor.

### Import data files from Amazon S3 to OceanBase Database

**Scenario**: Import all supported CSV data files from Amazon S3 cloud storage into the USERA schema (for OceanBase Database versions earlier than V4.0.0, provide the password of the sys tenant).

**Sample statement**:

```shell
$./obloader -h xx.x.x.x -P 2883 -u test@mysql#cluster_a -p ****** --sys-user **u*** --sys-password ****** -D USERA --csv --table '*' -f 's3://obloaderdumper/obdumper?region=cn-north-1&access-key=******&secret-key=******'
```

The `-f 's3://obloaderdumper/obdumper?region=cn-north-1&access-key=******&secret-key=******'` option specifies the storage path, which consists of the following components:

|  **Component** |**Description**|
|----------------------------------|--------------------------------------------------------|
|  `s3` | The [S3](https://docs.aws.amazon.com/zh_cn/s3/index.html) cloud storage type.|
| `obloaderdumper` | The name of the S3 storage space.|
| `/obdumper`  | The resource path of the S3 storage space. |
| `region=cn-north-1&access-key=******&secret-key=******` | Specifies the required parameters for the request.<ul><li>`region=cn-north-1` specifies the physical location of the S3 bucket.</li><li>`access-key=******` specifies the S3 access account.</li><li>`secret-key=******` specifies the S3 access key.</li></ul> |

### Import data from HBase to OBKV

**Scenario**: You can import data files in the SQL, CSV, ORC, and Parquet formats (with column names) from HBase to OBKV.

**Sample statement**:

```shell
$./obloader -h xx.x.x.x -P 2883 -u test@mysql -p ****** -D USERA --csv --table htable1 --hbase-cf family1 --hbase-rowkey column1 -f /Users/.../htable1.csv
```

**Parameters**:

* `--hbase-cf`: specifies the column family to which data is written.
* `--hbase-rowkey`: specifies the name of the rowkey column.
* `--hbase-rowkey-reverse`: specifies whether to reverse the rowkey column.

#### Example

Original table structure:

```sql
CREATE TABLE htable1(
column1 varchar(10),
column2 varchar(10),
column3 varchar(10)
);
```

Target table structure (must be created in advance):

```sql
CREATE
CREATE TABLEGROUP htable1;
CREATE TABLE htable1$family1 (
K varbinary(1024),
Q varbinary(256),
T bigint,
V varbinary(1048576) NOT NULL,
PRIMARY KEY(K, Q, T)
)TABLEGROUP = htable1;
```

#### Conversion rules

Original row:

| Column name | column1 (rowkey) | columnA | columnB | ... |
|------|-------------------|---------|---------|-----|
| Data row | v1 | v2 | v3 | ... |

obkv-hbase:

| Column name | K | Q | T | V |
|------|---|---|---|---|
| Data row | v1 | columnA | - | v2 |
| Data row | v1 | columnB | - | v3 |

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>The T column stores the current time in the format of a negative value of `System.currentTimeMillis()`. </p>
</main>
